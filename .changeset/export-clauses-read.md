A declaration an export clause names is exported

`function POST() {}` followed by `export { POST }` was reported `internal`, with nothing in `derivedBy` to say the module exports it, and so was every declaration exported through a clause: `export { handler as GET }`, `export { connect as default }`, `export type { T }`, `export { type T }`, `export { a as "x-y" }`. Only the `export` keyword on a declaration and a detached `export default name` were read. Every clause spelling is now read by the reader that already reads `export default name`: the declaration is `public`, and `derivedBy` carries `export-clause:<name>` for each name the module exports it under, so `export { handler as GET, handler as POST }` gives `handler` both `export-clause:GET` and `export-clause:POST`, after `export-keyword` when the declaration carries the keyword as well. `export { connect as default }` carries `export-default`, as `export default connect` does, so a default import of that module now resolves to `connect`, and a framework plugin that finds a page by its default export finds one written that way. A type-only clause or specifier is erased at runtime, so it exports only an interface or a type alias it names: `function handler() {}` with `export type { handler as GET }` stays `internal`. A re-export (`export { x } from "./y"`) binds nothing in the module and still marks no declaration, a clause naming an import declares nothing, and only the module's own statements are read, not a namespace's. The manifest declares the `export-clause` rationale prefix.

`visibility` is an input of the `api` fingerprint, so the `api` fingerprint of every declaration exported only through a clause moves, and `aburi diff` reports its visibility as changed. A call that now resolves to a clause's default export can change the effects its caller inherits, which with an effect plugin loaded moves that caller's `logic` fingerprint. An IR scanned before this release, compared with one scanned after, reports those Symbols as changed. On this repository, scanning one tree with both versions moves the `api` fingerprint of ten Symbols, nine plugin classes exported as `export { …Plugin }` and the docs site's `data`, and nothing else. Rescan the base rather than comparing against a stored IR. `aburi diff <base>..<head>` scans both sides with the installed plugins and is unaffected.
