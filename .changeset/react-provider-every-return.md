A function component is now a `framework:react:provider` when any of its returns hands back a `<X.Provider>` element, not only when the first `return` holding JSX does. A loading guard above the provider (`if (user === undefined) return <Spinner />`) made it a `framework:react:component`, while the same guard written `return null` kept it a provider. Every `return` in the function's own body is read, and a `return` in a nested function, generator or method belongs to that function. Each returned value, and a concise arrow's body, is read through `as`, `satisfies`, `!` and parentheses, into both arms of a conditional, both sides of `||` and `??` (only the left when it is an element, which is never falsy or nullish), and the last operand of `&&`. So `const AuthProvider = ({ user, children }) => (<AuthContext.Provider value={user}>{children}</AuthContext.Provider>)` and `return loading ? <Spinner /> : <AuthContext.Provider value={user}>…</AuthContext.Provider>` are providers too, where both were components. Only the returned element itself is read, not one inside it: a provider the function returns inside a call or an array (`return items.map((item) => <Ctx.Provider value={item} />)`, `return [<Ctx.Provider value={1} />]`) made it a provider and now leaves it a component, and so does one returned by a generator expression (`function* () {}`) nested in it, which the old reader counted as the function's own return. A provider inside a fragment or another element, and React 19's `<Ctx value={…}>` spelling, are components as before; the README lists them. `findReturnedJsxElementNames` is exported, and `findReturnedJsxElementName` returns the first of those names, so its answer changes in three ways: a parenthesised concise body gives the element's name where it gave `null`, a returned call or array gives `null` where it gave the name of an element inside it, and a fragment returned before a named element (`if (x) return <>a</> ; return <Ctx.Provider />`) gives that element's name where it gave `null`, because a fragment has no name and is skipped.

The `api` fingerprint reads `extKind`, so it moves for every function this reclassifies between `framework:react:component` and `framework:react:provider`. An IR scanned before this release, compared with one scanned after, reports those Symbols as api changes. Both are `framework:` extKinds, so the Markdown projection's Boundary effect surface lists the same Symbols. Rescan the base rather than comparing against a stored IR. `aburi diff <base>..<head>` scans both sides with the installed plugin and is unaffected.
