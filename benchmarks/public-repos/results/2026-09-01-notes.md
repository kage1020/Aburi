# Notes on the 2026-09-01 run

Read alongside [`2026-09-01.md`](./2026-09-01.md), which holds the tables, and
[`2026-09-01.json`](./2026-09-01.json), which holds every sample.

Environment: 4 vCPU Intel Xeon @ 2.10 GHz, 16 GiB RAM, Linux, **Node v22.22.2**
— two major versions behind the `>=24` this repo declares, because that is what
the machine offered. Nine repositories, 1 warmup plus 3 measured scans each,
`aburi` 0.3.0 built from the working tree.

## The roadmap's performance target is already met, single-threaded

[roadmap.md](../../../docs/roadmap.md) files "1,000-file scan in under 30
seconds" under *Later*, and [performance.md](../../../docs/design/performance.md)
§2 sets the SLA at ≤ 30 s wall and ≤ 2 GiB peak RSS for 1,200 files on 4 cores.
On the same class of runner, with no worker pool at all:

| | Files | Scan | SLA |
|---|---:|---:|---:|
| `tanstack-query` | 1,081 | **3.7 s** | 30 s |
| `nest` | 1,914 | **3.9 s** | 30 s |
| `cal-com` | 5,002 | **14.7 s** | 30 s |

Peak RSS never passed 466 MiB on a scan, against a 2 GiB budget. Cost is linear
in file count — a least-squares fit over all nine repos gives **2.8 ms per file
plus 326 ms fixed** (grammar load and config), and every repo sits within
2.1–5.2 ms/file once the fixed cost is amortised. `zustand`'s 8.7 ms/file is 49
files paying that fixed cost on their own, not a per-file cost.

This does not make [performance.md](../../../docs/design/performance.md) wrong,
but it does move it: the pool would buy roughly 4× on a workload that already
finishes 8× inside its budget. The scans worth being impatient with are `aburi diff`'s,
which run two of them (measured ratio 1.7–2.2× a single scan) — and those are two
*independent* scans, which is a cheaper parallelism than sharding one.

## Determinism holds

Three consecutive `aburi scan --no-timestamp` runs over an unchanged tree
produced byte-identical IR on all nine repositories — the single-threaded form of
performance.md PF11, now measured on 13,742 real files rather than a fixture.

## Two extraction defects, found by pointing it at code it had never seen

**1. A quoted non-identifier class member aborts the file** (`zod`, exit 3).

```
packages/zod/src/v3/types.ts: qualified name ""~validate"" contains the
non-identifier segment ""~validate""
```

`zod` v3 declares `"~validate"` as a class member — legal TypeScript, and the
Standard Schema interface has made `~`-prefixed members a convention rather than
a curiosity. The qualified-name rule rejects the segment, the plugin throws, and
the whole file lands in `stats.skippedFiles` as `extraction-failed`, taking every
other symbol in it along. `zod` is the only repo here that exits non-zero.

**2. An unescaped `&` in JSX is a recoverable parse error** (`shadcn-ui`, 115
files — 110 `.tsx`, 3 `.ts`, 2 `.js`).

Minimal reproduction, with the `tsx` grammar this plugin already routes `.tsx` to:

```tsx
export function A() {
  return <p>Subscription & Billing</p>          // syntax error at the &
}
export function B() {
  return <a href="https://x.test/?a=1&b=2">x</a> // syntax error at the &
}
export function C() {
  return <p title="a & b">x</p>                  // clean — & not entity-shaped
}
```

So: a bare `&` in JSX *text*, and an entity-shaped `&…` inside a JSX attribute
value with no closing `;`. Both are ordinary prose and ordinary tracking URLs,
which is why one component library trips it 110 times.

Recovery works — a targeted repro kept both the symbol and a call sited after the
error — so this is not a demonstrated loss of data. It is not free either:
`aburi diff` warns that files with recoverable parse errors "reached the IR
rather than `stats.skippedFiles`, so nothing marks them as doubtful", and on a
React codebase that warning now fires on 3% of files as a matter of course, which
is the number at which people stop reading it.

## Call resolution is the honest weak spot

| Repo | Calls | Resolved | Dynamic | External | Local scope | No match |
|---|---:|---:|---:|---:|---:|---:|
| `zod` | 5,245 | 18.7% | 261 | 287 | 692 | 3,022 |
| `hono` | 4,825 | 15.8% | 804 | 64 | 483 | 2,710 |
| `trpc` | 5,209 | 14.0% | 469 | 876 | 442 | 2,691 |
| `shadcn-ui` | 20,559 | 9.5% | 1,191 | 6,795 | 1,068 | 9,561 |
| `cal-com` | 51,535 | 6.5% | 8,278 | 14,283 | 3,283 | 22,339 |
| `nest` | 9,761 | **2.0%** | 3,591 | 2,056 | 870 | 3,052 |

The roadmap already says call resolution is syntactic and that LSP enrichment is
next; these are the numbers that says how much it is worth. `nest` is the extreme
and the explanation is in its own shape: dependency injection means a call site's
callee is a constructor-injected interface, which no amount of syntax can follow,
and `dynamic` is its largest unresolved bucket at 3,591.

`no-match` is the largest bucket almost everywhere (58% of `zod`'s unresolved,
46% of `nest`'s). It is also the least self-explanatory of the five — worth a
sample-and-classify pass before LSP work starts, because whatever fraction of it
is a resolver gap rather than a genuinely unknowable callee is fixable without
type information.

## Caveats

- One machine, one run, one commit per repo. Wall times move with the runner;
  the ratios and the counters do not.
- Node 22, not the declared 24.
- `init` detected what it detected — no effects plugin was force-enabled, so
  `cal-com`'s Prisma and tRPC call sites are counted as ordinary calls here.
- `base` is `head~50` for every repo, which is a larger change set than a normal
  pull request. It stresses the diff engine's projection, not its scan.
